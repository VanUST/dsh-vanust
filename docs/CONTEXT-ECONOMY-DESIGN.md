# Экономика контекста: дизайн изменений

**Дата:** 2026-11-12 · **Гарнесс:** `@deepseek-ai/dsh@0.2.1-rc.2`, профиль `web` ·
**Источники цифр:** выгрузка платформы `usage_data_2026-10-14_2026-11-12.zip` и логи сессий
`$DSH_HOME/sessions` (183 сессии с usage, 40 880 шагов, ноябрь).

Документ — **проект**: ничего ещё не включено. Каждое изменение оценено по измеренным данным;

## 0. TL;DR

Расход определяют три множителя: **число шагов × контекст на шаг × цена токена**. Сейчас шаг в
среднем стоит $0.0021 и несёт 351 тыс. токенов контекста, из которых 252 тыс. — переотправленное
прошлое. Существующие слои сжатия почти не работают на этой нагрузке: RTK отфильтровал 7
результатов из 33 966, headroom экономит 0.34% при +5 с задержки.

| # | Изменение | Слой | Ожидаемый эффект | Риск | Откат |
|---|---|---|---|---|---|
| P1 | `thresholdRatio` 0.8→0.5, `retainRatio` 0.16→0.08 | конфиг профиля | −8…−10% | раньше теряется контекст | 4 строки |
| P2 | Потолок сессии ~300–400 шагов | правило агентов + дисциплина | −15…−20% | дробление задач | снять правило |
| P3 | Проекция вывода `run_code` (8 КБ + баннер + spill) | новый плагин на `tools/post-execute` | −5…−7% | обрезка нужного вывода | выключить ряд |
| — | headroom: не включать в загрузку | уже есть, opt-in | 0 (0.34%) | +5.2 с на запрос | — |
| — | RTK: оставить как есть, не расширять | уже есть | ~0.02% | — | — |

Реалистичная цель — **−25…30%** счёта: ~$72–77 за две недели вместо $103.41.

## 2. Принципы дизайна

1. **Сжимать на входе, не в истории.** Сжатие безопасно только там, где текст попадает в контекст
   (хвост): RTK, будущая проекция `run_code`, окно изображений. Переписывание прошлого дороже:
   остаток пересчитывается по цене cache-miss (55×).
2. **Одна голова — одна компакция.** Единственная санкционированная правка истории — суммаризация
   по порогу. Не добавлять вторую (ad-hoc прунинг старых результатов), пока не измерено, что она
   окупает потерю кэша.
3. **Мерить шагом.** Метрики: $ на 1 000 шагов, медиана и распределение контекста, число
   компакций, доля шагов >500 тыс., шагов на задачу. Считать существующим инструментом.

## 3. Изменения

### P1 — компакция ниже и «мельче» (конфиг, обратим двумя строками)

**Что.** В трёх группах компакции профиля (`cordis.patch.yml`, строки ~486, ~556, ~631 — пресеты
`orchestrator` и специалистов) задать явно:

```yaml
- id: compaction-basic
  name: '@deepseek-ai/dsh-compaction-basic'
  config:
    thresholdRatio: 0.5      # 500 000 вместо 678 464
    retainRatio: 0.08        # 59 556 вместо 119 111
```

**Почему обе ручки.** `retain` — то, что после компакции остаётся и оплачивается на каждом
следующем шаге по цене cache-hit. Держать 119 тыс. «про запас» дороже, чем перечитать нужное.

**Ожидаемый эффект.** Цикл контекста меняется с ~179↔678 тыс. (средний ~428 тыс.) на
~80↔500 тыс. (средний ~300 тыс.): −30% на переотправленное прошлое = −10.8% счёта. Из этого
вычитаются накладные: каждая компакция — запрос-суммаризатор (≈$0.0015, префикс кэширован) плюс
одна переотправка удержанной части по цене промаха (≈$0.013). При шаге роста ~1.2 тыс. токенов
компакция будет раз в ~350 шагов; в топ-сессии это 8 компакций вместо 5, дополнительно ≈$0.1.
**Итог: −8…−10%.**

**Риск.** Раньше теряется контекст — вероятны повторные чтения и рост числа шагов, что съест часть
выигрыша. Это и есть параметр, который проверяется неделей замера.

**Откат.** Вернуть две строки конфига; миграции данных нет.

### P2 — потолок длины сессии (правило + дисциплина)

**Что.** Правило: одна задача — одна сессия; перед следующей подзадачей `/compact` и новый чат;
чат длиннее ~300–400 шагов считается аварийным. Место — policy-текст оркестратора
(`plugins/orchestrator/orchestrator.mjs`; там есть чужие незакоммиченные правки — трогать
отдельной задачей) либо только дисциплина без кода.

**Почему.** 4 сессии ≥2 000 шагов = 26% счёта, ещё 15 сессий 500–1 000 шагов = 27.6%. Стоимость
сессии растёт примерно квадратично от числа шагов: шаг №1 000 оплачивает всю историю.

**Ожидаемый эффект** (модель по реальным кривым, верхняя граница): перезапуск каждые 400 шагов —
−23.7%, каждые 800 — −14.3%, каждые 200 — −40.1%. Реалистично достижимо около половины:
**−15…−20%**.

**Риск.** Дробление теряет контекст: новая сессия требует брифинга (1–2 тыс. токенов) — дешевле,
чем 1 000 шагов по 400 тыс., но заметно по времени.

**Откат.** Снять правило.

### P3 — проекция вывода `run_code` (плагин, требует реализации и доказательства)

**Что.** Плагин на `tools/post-execute` по образцу RTK, но для `run_code`: результат больше порога
(предлагается 8 КБ) заменяется на «голова 4 КБ + хвост 1 КБ + строка-баннер + путь к полному файлу
в `$DSH_HOME/spill/`». Полный текст агент достаёт `read`-ом по offset/limit. К ошибкам и
ненулевым кодам проекция не применяется — как RTK, который не прячет маркеры.

**Почему.** Вывод инструментов — 45.5% контекста, из них `run_code` 96%; 893 вызова дают 15.6 МБ
(>8 КБ), это ~21% содержимого контекста.

**Ожидаемый эффект.** При пороге 8 КБ −15…20% контекста ⇒ **−5…−7% счёта**. Без баннера и spill
эффект обернётся ростом числа шагов.

**Риск.** Двойное чтение: агент полезет за полным текстом. Проверяется числом последующих `read`
в тех же сессиях.

**Откат.** Удалить ряд плагина — он ничего не мутирует в данных.

### Не делать

| Идея | Почему нет |
|---|---|
| Включить headroom в загрузку | 0.34% экономии при +5.2 с на запрос; он переписывает запрос целиком и рушит кэш-префикс — ровно то, что даёт 55× разницу цен |
| Расширять RTK | `bash` даёт 0.8 МБ против 33.3 МБ у `run_code`; покрытие 0.02% — не рычаг |
| Резать системный префикс (36 тыс. токенов) | 36 тыс. × 40 880 шагов × 3e-9 ≈ **$4.4** за две недели; чистить стоит ради качества промпта, не ради денег |
| Прунить старые результаты между компакциями | правка головы рушит кэш: 55× на весь остаток контекста, дороже сэкономленного |

## 4. Проверка и откат

**Базовая линия:** одна неделя без изменений — берётся из следующей выгрузки `usage_data_*` плюс
`node scripts/session/session-report.mjs`.

| Метрика | Сейчас | Гейт |
|---|---|---|
| $ на 1 000 шагов | $2.10 | −15% или лучше |
| медиана контекста на шаг | 337 тыс. | ≤ 300 тыс. |
| доля шагов >500 тыс. | 25.6% | ≤ 15% |
| компакций на 1 000 шагов | ~1.8 | рост не более +50% |

Гейт «шагов на задачу» — защита от того, чтобы экономия не оплачивалась повторной работой.

**Порядок:** P1 один, неделя замера; затем P2; P3 — только после того, как P1+P2 измерены, и с
собственным доказательством на одной неделе.

**Общий критерий откатa:** если за неделю $/1 000 шагов не упали хотя бы на 10% или шагов на задачу
стало больше на 20%, изменение снимается целиком; частично оставленных ручек не остаётся.

## 6. Контракты новых плагинов P2 и P3

Оба — самостоятельные пакеты в стиле `plugins/rtk` (`package.json` + один `.mjs` + `README.md`),
peerDependency `@deepseek-ai/cordis`. Ни один не правит профиль: ряд композиции добавляет
оркестратор.

### 6.1 `@cc/dsh-session-budget` (P2)

**Шов.** Хост-плагин на том же событии, на котором живёт компакция (`agent/pre-step` в
`dsh-compaction-basic` — там же видно, как вставить сообщение в поверхность диалога). Счётчик шагов
берётся из записей сессии, а не из контекста, поэтому переживает компакцию.

**Конфиг и поведение.**

| Поле | Значение | Смысл |
|---|---|---|
| `softSteps` | 300 | первое мягкое напоминание |
| `repeatEvery` | 100 | повтор, пока сессия продолжается |
| `hardSteps` | 500 | жёсткая формулировка |
| `handoffDir` | `docs/handoffs` | куда агент пишет документ |
| `enabled` | true | выключатель без удаления ряда |

Таблица срабатываний: 299 — тишина; 300 — мягкое; 400 — мягкое повторно; 500 — жёсткое; на том же
номере шага повторного сообщения нет. Никаких вызовов модели: текст фиксированный.

**Текст напоминания (фиксированный, не генерируемый).** Агенту: «ты на шаге N; прежде чем
продолжать, сделай handoff в `<handoffDir>/<YYYY-MM-DD>-<slug>.md` с разделами State / Decisions /
Open questions / Next steps / Commands; зарегистрируй файл в текущей задаче (`task_note` +
`resultArtifacts`); скажи человеку, что продолжать лучше в новом чате с этим файлом». Человеку:
короткая карточка/уведомление с номером шага, длиной сессии и путём к handoff-файлу.

**Чего плагин не делает.** Не останавливает ход, не бросает исключение в агента (всё в `try/catch`
+ лог), не вызывает модель, не трогает другие сессии, не отправляет уведомление повторно на том же
шаге.

**Доказательство.** Фикстура с фальшивой сессией на N шагов: проверка таблицы срабатываний,
отсутствия дублей и того, что ниже порога не вставлено ничего. Плюс прогон на втором сервере
(`dsh --profile web --patch ...`), чтобы напоминание реально доехало до контекста.

### 6.2 `@cc/dsh-run-code-projection` (P3)

**Шов.** `tools/post-execute` для инструмента `run_code` — по образцу `plugins/rtk/rtk.mjs`, который
уже доказал, что этот шов умеет заменять модельное представление результата.

**Конфиг.**

| Поле | Значение по умолчанию | Смысл |
|---|---|---|
| `tools` | `['run_code']` | какие инструменты проецируются |
| `maxChars` | 8000 | выше — проецировать |
| `headChars` / `tailChars` | 4096 / 1024 | что остаётся в контексте |
| `spillDir` | `.dsh/spill` | внутри workspace, чтобы `read`/`grep` доставали файл |

**Правила.** Проекция применяется только к только что полученному результату (хвост, кэш цел) и
только если: текст длиннее `maxChars`, блок не является изображением, результат не помечен ошибкой,
полный текст успешно записан в spill-файл. Иначе результат проходит без изменений.

**Баннер (одна строка, всегда на виду):**

```
[projection: run_code output 41 208 chars -> shown 5 120; full text .dsh/spill/<session>/<callId>.txt — read it with offset/limit or grep it]
```

**Идемпотентность.** Результат с баннером не проецируется повторно; маркер — сам баннер.

**Доказательство.** Фикстура из реального `tool/result` вызова `run_code` (из лога сессии):
большой результат проецирован и полный текст читается по названному пути; короткий, ошибочный и
уже проецированный — не тронуты; измерено сокращение символов до/после.

### 6.3 Интеграция (после обоих плагинов)

1. `scripts/pack-plugin.mjs` → tarball в `plugins/`.
2. Ряд в `plugins/inventory.json` (`mounted: true`) и в `profile/cordis.patch.yml` kit-а.
3. Установка tarball-а в живой профиль (`package.json` + pnpm install) и ряд в живом патче.
4. Перезапуск сервера web — единственный шаг, который видит человек; без него ни P1, ни P2 не
