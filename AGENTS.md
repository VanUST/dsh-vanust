# dsh-kit artifacts

**This is the artifact table.** It says what each artifact under this repository is, what
owns it, and the command that fails when it is wrong. `README.md` describes the deployment
to a person; this table describes it to an agent, which needs the enforcement point rather
than the prose.

The kit root declares itself in `.dsh/project.json`: its `languages`, its `verification`
commands, the `rules` it claims, each naming the command that fails when the rule is
broken, and the `ratchet.zones` a change may touch. That file, not this one, is what the
`context_*` tools and the ratchet read. Where the two disagree, the manifest is right and
this table is a defect.

| Artifact | What it is | Owner | The command that fails when it is wrong |
|---|---|---|---|
| `rules/AGENTS.md` | the deployment's binding operating rules, installed to `$DSH_HOME/AGENTS.md` | human (`deployment-rules` is `proposeOnly`) | `node scripts/check-instruction-routing.mjs`; `node scripts/drill-kit-rules.mjs --root .` |
| `rules/DEPLOYMENT.md` | the operator's procedure: install, start, converge, upgrade | human | `node scripts/check-instruction-routing.mjs` (every mounted plugin named, every script it names present) |
| `rules/drills/*.json` | one behavioural scenario per prompt rule, RED/GREEN differential | human | `node scripts/drill-kit-rules.mjs --root .` (`--plan`) and `node --test scripts/test-drill-kit-rules.mjs` |
| `docs/adrs/*.adr.md` | the decisions, each citing content-hashed reasoning under `docs/ratchet/sources/` | human, for authority | `node plugins/ratchet/ratchet-cli.mjs compile --root .` |
| `docs/specs/*.md` | generated law cards — **never hand-edit** | generated | `node plugins/ratchet/ratchet-cli.mjs compile --root .` (`SPEC_HASH_MISMATCH`) |
| `plugins/inventory.json` | the shipped plugin set and each row's provenance | human | `node scripts/check-portability.mjs` |
| `plugins/*.tgz` | the packed plugins machines install | generated | `node scripts/check-portability.mjs` (tarball matches source; a repack carries a new version) |
| `plugins/ratchet/` | `@cc/dsh-ratchet`: decisions compiled into laws a command verifies | `shipped-plugins` | `node --test scripts/test-ratchet.mjs`, `node --test scripts/test-ratchet-guard.mjs` |
| `plugins/kit-rules/` | `@cc/dsh-kit-rules`: `$DSH_HOME/AGENTS.md` into every system prompt | `shipped-plugins` | `node scripts/probe-dsh-api.mjs --kit-rules` |
| `plugins/work-modes/` | `@cc/dsh-work-modes`: the `subagent` concurrency cap and the per-session work mode | `shipped-plugins` | `node --test scripts/test-work-modes.mjs`, `node scripts/probe-work-modes.mjs` |
| `plugins/dsh-adr-panel/` | `@cc/dsh-adr-panel`: the browser window on the decisions and specs | `shipped-plugins` | `node scripts/test-adr-panel.mjs` |
| `plugins/dsh-context/` | `@cc/dsh-context`: a project's modules, rules and work orders as tools | `shipped-plugins` | `node scripts/check-portability.mjs` |
| `plugins/presentation/` | `@cc/dsh-presentation`: a deck spec into a standalone HTML file | `shipped-plugins` | `node --test scripts/test-work-modes.mjs` shares the harness; `node scripts/check-portability.mjs` |
| `profile/cordis.patch.yml` | the canonical profile: which rows are mounted, and what reaches the prompt | `deployment-rules` | `node scripts/check-instruction-routing.mjs` |
| `scripts/*.mjs` | the kit's own checks, tests and probes | `kit-tooling` | each is a `verification` entry in `.dsh/project.json` |
| `probes/api-probe/` | the throwaway plugin a probe mounts to measure harness APIs | `kit-tooling` | `node scripts/probe-dsh-api.mjs`, `node scripts/probe-work-modes.mjs` |
| `.dsh/project.json` | the project's declaration of languages, commands, rules and zones | human | `node scripts/check-zone-coverage.mjs --root .` |
| `.dsh/ratchet/` | machine-written state: specs, state, the append-only ledger, contradictions | generated | `node plugins/ratchet/ratchet-cli.mjs verify --root .` |
| `reports/ratchet/` | compile, verify and review reports | generated | regenerated by the commands above |

**Rules are real only where a command fails.** `context_rules` answers which rule this
project claims and the exact command that fails when it is broken — including the rules
that cite no command, which it reports as unverified. Ask it rather than reading this
table.

**Unverified claims, named rather than buried.** Two rules in `.dsh/project.json` cite no
enforcement point: `flash-only-models` (the veto exists and the release gate probes it, but
nothing checks that the gate is ENABLED outside a throwaway profile) and `pin-the-harness`
(the pins exist; no command compares them). They are `pendingReason` entries, and
`LIMITATIONS.md` lists them with every other limit.
